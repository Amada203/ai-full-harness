# 多工具连续开发与授权补充规格

状态：待用户确认；不是实施完成或权限授权。日期：2026-09-05。

## 目标与边界

同一项目在不同模型、开发工具和机器之间保持可核对的连续进度。
适用对象包括 Harness 源码、独立 Autopilot 源码和新生成的消费者项目。
工具入口共用规则、当前状态及历史，不复制不同版本的事实。
自动化负责观察、验证和准备；事实记录不是人工批准，也不是运行权限。
不承诺零故障、模型理解一致、找回未落盘内容或抵抗管理员改写。

## 1. 默认生成器注册

安装应区分“可选显式触发”与“默认新项目触发”，默认切换必须显式选择。
现有安装器仅支持前者；本规格不声称已有默认切换命令。

先确认稳定安装根目录及版本，再展示每个工具的目标配置差异。
只迁移已识别且成对的旧生成器标记区块，保留其他个人指令。
重复/残缺标记、符号链接目标、并发编辑、未知旧规则均停止并报告。
写入前备份，使用内容比较及原子替换；恢复时如用户已修改文件，不能
直接覆盖，要展示冲突。重复运行不得增加重复触发器。
不能把临时 worktree 注册为长期默认入口；不能硬编码另一台电脑路径。
全局写入需另行审批。修改后必须在新任务中验证实际路由，不只检查文字。

## 2. 检查点和恢复

推荐用一个机器可读检查点描述最近一次已核实工作状态，包含：

- schema、项目身份、仓库根/工作树身份、分支、HEAD 或明确的无提交状态；
- index 与工作区差异、未跟踪文件的边界内摘要、子模块与冲突状态；
- 当前阶段、已核实目标、未完成事项、下一允许动作、待用户决策；
- 测试命令、退出码、对应输入摘要；没有证据不得记为通过；
- 相关架构/契约/Gate 指纹、工具与 Harness 版本、同步状态。

摘要扫描不读取或复制密钥内容，不跟随越界符号链接；忽略目录不能被
用来掩盖已跟踪文件变化。未知扫描范围需标为无法判定，不能报告无变化。
检查点自身及派生展示排除自引用摘要；写入原子化，保留上次有效记录。
检查点只是本地证据，不是可抵抗仓库写入者伪造的信任根。

在每个工作单元开始/完成、验证完成、发现阻塞和计划切换工具时记录。
新工具启动前统一执行只读恢复检查：缺记录、损坏、HEAD/分支变化、
脏文件变化、冲突或旧测试证据均产生明确分类及恢复报告。
一致不代表业务正确，只代表检查范围内未发现变化。

恢复默认不重置代码、不自动接受新需求、不刷新通过状态、不执行任意
上一模型留下的命令。仅在原授权及可信测试命令范围内重验；批准需求、
权限提升、重构方向改变必须交用户。更新语义进度要保留依据和不确定项。
不依赖某一产品的 hook 才能工作；支持 hook 的工具可自动调用同一命令，
无 hook 时依靠启动入口及可验证检查。必须披露这种强制能力差异。

## 3. 重构协议

重构前记录当前行为/接口/数据约束、已知失败、脏文件及可恢复基线；
创建 Git 提交或远程分支仍遵循独立审批，不能借基线名义偷偷提交。
在独立变更范围实施，保留第一性原理问题定义及 U 型根因分析。
更新架构、技术契约和风险；受影响 Gate 失效，不能复用过期验收。

每个重构增量含行为对照、冒烟/回归及下一步交接。涉及存量数据时，
先演练兼容期、迁移、备份恢复与不可逆项；代码回退不等于数据恢复。
未验证的破坏性回退不得自动执行。异常时暂停增量并报告真实可恢复范围。
最后对抗审查至少覆盖旧调用方、旧数据、部分迁移、重复执行、中断、
性能回退和权限边界，再核对架构与实际代码。

## 4. 知识库初始化与同步

项目仓库为主要事实来源，Obsidian 为可追溯镜像，不进行隐式双向合并。
先展示 Vault、项目目录和允许同步文件清单；每个项目首次建目录必须
获得用户明确确认，批准前不能创建目录或持久化绑定。
本机绑定保存在不提交的本地配置；新机器重新确认本机路径。

批准后，在已授权目录内按工作单元、验证、决策、阻塞事件同步。
只同步允许的文档，不复制源码、日志、凭据或客户数据作为默认行为。
同名目录、符号链接、镜像被人工修改、路径变化、覆盖或删除须暂停确认。
部分失败保留待同步记录并重试去重，不报告同步成功、不删除用户文件。
不因镜像不可用回滚已完成的业务代码；应报告同步未完成。

## 5. GitHub 折中授权（待确认）

默认远程写入关闭。可选择提前批准仅候选分支/草稿 PR 的窄范围授权，
约束仓库身份、任务目标、路径、分支前缀、动作、有效期和次数/成本预算。
修改授权本身、过期、撤销、身份/证据不明或扩大范围立即阻断。
许可不能由项目清单中的 approved 字段自行产生；需外部可信审批来源。

默认分支合并、正式发布、部署和权限/密钥/工作流规则修改逐次审批。
自主候选操作不获得合并权限；高风险工作始终需要独立人工决定。
此方案要与尚待确认的中央控制账本及既有政策冲突检查一起设计，
不能在没有远程身份隔离的条件下只增添几个布尔配置就启用无人值守。
本规格被确认，也只授权后续本地实现，不授权创建仓库、秘密、App 或发布。

## 验收矩阵

| 要求 | 必须观察到的行为 |
|---|---|
| 默认注册 | 保留个人规则；重复安装幂等；冲突不写；可恢复；真实新任务路由正确 |
| 中断续接 | 无提交、脏工作区、分支切换、损坏记录、未跟踪文件变化均可识别 |
| 防止误续接 | 旧证据不会冒充新代码通过；恢复不执行记录中的恶意命令 |
| 多工具 | 两个源码项目和生成项目均由四种入口调用同一检查；真实换工具演练 |
| 重构 | 行为对照、Gate 失效、迁移中断与恢复演练有可重复证据 |
| 知识库 | 未确认零创建；重复同步幂等；手工改动不覆盖；失败可辨识 |
| GitHub | 范围内许可与范围外拒绝均通过；过期/撤销/伪造审批零后续写入 |

当前入口结构测试只覆盖矩阵的一小部分；没有该表对应实证不得整体验收。

## 实施顺序

确认本规格后：检查点只读模型与反例 → 记录/恢复命令 → 三类项目接入
→ 重构记录及恢复演练 → 知识库预览/确认/同步 → 注册迁移预览与回滚。
GitHub 窄授权执行最后接入可信控制平面；远程配置与实际写入单独审批。
每一步使用反例驱动，并同步已授权的现有 Obsidian 项目记录。
